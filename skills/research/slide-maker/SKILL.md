# slide-maker：論文投影片製作

## 目的

產出一份能完整說明整篇論文的投影片，**定位是「使用者通盤理解這篇論文」**，不是打磨過的報告簡報。

- **完整性優先於精簡**：論文每一節的重點都必須出現在投影片上，不可為了版面好看而略過章節（Related Work、Discussion、Appendix 也算）。
- 若之後要優化成組會／口試報告（精簡、加強敘事節奏、控制在 N 分鐘內），那是另一個階段的工作，交由其他 agent 或另一次任務處理，本 skill 不為此犧牲完整性。

## 前置檢查

1. 讀取該論文資料夾的 `README.md` 與 `supplements.md`。
2. 確認使用者的背景知識足夠：所有關鍵概念的理解程度至少為「懂」。
   - 若仍有「不懂」或「略懂」的概念，先提醒使用者回去執行 `background-extension`，或經使用者同意後繼續。

## 執行步驟

1. **蒐集素材**
   - 從該論文資料夾的 `paper.pdf` 取得所有圖表（figures / tables）並抽取圖片；無法抽取時，明確告知使用者哪些圖需要手動補上，並在投影片留好位置與說明。
   - 整理論文中的重要公式。

2. **產出大綱，先給使用者確認**（不要直接開始做投影片）
   - **敘事立場：這份簡報是「作者用它來表達自己的想法」，不是「使用者理解後的心得整理」。**
     - 章節順序**依論文本身的先後順序**編排，不可為了好懂而重排。
     - 用作者的框架與術語陳述，不要把 agent 自創的教學比喻寫進正文。
     - supplements.md 的白話教學是「使用者為了讀懂論文而搭的鷹架」，屬於個人理解，**放進投影片備註（speaker notes）**供報告時參考，不進正文改變論文敘事。
     - 同理，與使用者自身專案的關聯也不放正文（除非使用者明講要）。
   - 條列每一頁的頁碼、標題、以及該頁要放什麼（重點／公式／哪張圖／數據），並標注對應論文的章節或公式編號。
   - **內容清單依論文實際結構調整**。下列是「標準實證論文」的預設清單，但論文類型不同結構就不同：
     - 封面：論文標題、作者、發表處、年份
     - **目錄**：依論文章節列出，每項標注對應頁碼
     - 背景介紹：研究動機、要解決的問題、必要的前置知識（取自 supplements.md）
     - 方法：核心概念與**重要公式**（每條公式附白話解釋）
     - **論文中所有的圖表**：每張圖一頁或合理分配，附上圖文說明（caption 的翻譯與解讀）
     - 實驗過程：資料集、實驗設定、比較對象、結果分析
     - 結論：貢獻、限制、未來方向
   - **調整規則**（不可硬湊、不可漏收）：
     - 論文**沒有**的區塊就不放，並在大綱標注「本篇無」讓使用者確認，**不要為了填滿清單而編造內容**。例：綜述論文沒有自己的實驗、理論論文可能沒有圖、系統論文可能沒有核心公式。
     - 論文**有、但清單沒列**的區塊要自行補上。例：綜述的分類體系與比較表、理論論文的定理與證明脈絡、資料集論文的蒐集與標註流程、系統論文的架構圖與效能量測。
     - 判準只有一條：**論文花篇幅講的，投影片就要有**（呼應「完整性優先」）。
   - **等使用者確認或調整後才進入下一步**——一份投影片產生＋QA 要數分鐘，結構錯了整批重做的成本遠高於先確認。

3. **確認風格**
   - 提供 2–3 個選項讓使用者挑（或直接給推薦值），至少涵蓋：
     - 配色（例：深色沉穩／淺色清爽／領域相關色，如 NVIDIA 論文用綠）
     - 語氣與密度（口頭報告用＝字少圖大；自我複習用＝資訊密度高）
     - 用途（組會報告／課堂報告／口試／純自己複習）——用途會影響頁數與深度
   - 使用者沒意見時，採用推薦值並明講採用了什麼，不要默默決定。

4. **製作投影片**
   - 使用 pptx skill 產出 `.pptx` 檔案；若環境不允許，改產出 Markdown 格式的投影片（如 Marp）。
   - **語言：中英文並列**。標題與每個要點都要有英文與繁體中文；英文優先採用論文的原始措辭與術語（作者怎麼說就怎麼寫），中文是翻譯。
     - 公式照論文原樣呈現；避免整段複製論文長段落（版權考量，且整段文字貼上投影片也無法閱讀）——用論文的術語與框架把該段重點寫成投影片語句即可。
   - **備註（speaker notes）一律用高中程度就能懂的白話中文**，補充正文的專業術語與公式在說什麼（原則同 background-extension：名詞先解釋、一階一階搭）。正文負責「作者怎麼說」，備註負責「這句話是什麼意思」。
   - **每頁都要有頁碼**（封面除外），位置固定於右下角；深色頁與淺色頁各用可辨識的顏色。
   - 公式排版的已知地雷（皆已踩過，見 dev-log）：
     - 投影片沒有 LaTeX：`x_g`、`argmin_q̈` 這種底線寫法會把底線直接印出來。要用 PowerPoint 真正的上下標格式（pptxgenjs 的 `subscript` / `superscript`），或改寫符號。
     - **上下標若含數學字母（𝒳、𝒬 等 BMP 以外字元），必須用 `String.fromCodePoint` / 大括號整組取用**——這些字是 UTF-16 代理對，逐字元切割會把它切成兩半，顯示為兩個 `?` 方框。
     - **內文項目符號中絕對不能出現 `^` 或 `_`**：pptxgenjs 會在該處把段落切斷，導致項目符號消失、句子從中間斷行（例如 `ℝ^(k×k)` 會斷成兩段）。
       符號留在公式卡片裡；內文改用 Unicode 上下標（上標 ᵏ ˣ ⁱ ᵈ ᵀ ⁺，下標 ᵢ ᵣ ₀ ₁ ₂）或直接用文字敘述。
       產出前用 `grep -n 'en: "[^"]*[\^_]' 產生器檔案` 掃過一遍，確認條列文字裡沒有殘留。
     - **字型缺字**：Unicode 數學字母區（U+1D400–U+1D7FF）的花體／粗體／哥德體字母在一般字型（Arial 等）常缺字，會整個消失不見。改用 Letterlike Symbols 區的等價字元：`ℛ ℬ ℰ ℱ ℋ ℐ ℒ ℳ ℜ ℨ ℕ ℤ ℚ ℝ ℂ`。實測案例：`𝓡`（U+1D4E1）在 Arial 消失，換成 `ℛ`（U+211B）正常。這類字元只放在數學字型（Cambria）的公式卡片中最安全。

5. **QA（必做）**
   - 跑 pptx skill 的 `validate.py`，確認檔案不會壞。
   - 轉成圖片逐頁看過：文字溢位、重疊、間距不均、公式排版錯誤。修好再交付。

6. **講稿與音檔（使用者要求時）——產出兩份，不是一份**

   兩份**搭配同一份投影片**，都要能邊聽邊對照畫面。理由：完整版動輒 50 分鐘以上，第一次聽沒有框架可掛，吸收率差；先用骨架版建立框架再聽完整版，效果好很多（先給架構再填細節）。

   **（a）骨架版　`<論文資料夾名>-narration-brief.md`／`.m4a`，約 10 分鐘**
   - 用途：第一次接觸時先聽，建立整體框架。
   - 只回答四個問題：**解決什麼問題 → 核心想法是什麼 → 具體怎麼做 → 憑什麼相信有效**，最後補結論與限制。
     - 第四個問題依論文類型換算：實證論文＝實驗證據；理論論文＝證明與保證；綜述＝分類體系為何合理、依據多少文獻；系統論文＝實際部署與效能數字。
   - 只挑「承重」的骨幹頁，**約佔完整投影片的一半**（本篇 27 頁取 14 頁），其餘明講「細節在完整版」。
   - **挑法不是均勻壓縮，是挑承重結構**：能讓人瞬間理解核心的關鍵例子（例如本篇兩側障礙物抵銷的思想實驗）即使是「細節」也必須留，抽掉核心想法就只剩抽象定義。
   - 除了四個問題，還要留三樣**支撐框架的東西**，少了它們框架會空：
     1. **核心名詞的直覺**（本篇：度量＝一把偏心的尺）——不解釋清楚，後面所有機制都掛不上去
     2. **框架的野心**（本篇：慢迴圈的優化器也能包裝成 RMP，所以規劃與反應式在此是同一種東西）——這是「為何值得讀」的理由
     3. **限制**（本篇：局部極小、度量仍靠手工設計）——只講優點的骨架會給錯印象
   - 不要為了湊時間硬加內容，也不要為了短而砍掉上面三樣；長度是結果不是目標。
   - ⚠️ **括號內的「本篇：」是實例，用來說明該項是哪一「種」東西，不是模板。** 換一篇論文時要找的是**同一種**東西（這篇的核心名詞是什麼、這篇的野心是什麼），不是找「類似的內容」。若新論文確實沒有對應的東西，就在大綱標注沒有，不要硬湊一個出來。這個原則適用本檔案所有標注「例：」「本篇：」的地方。

   **（b）完整版　`<論文資料夾名>-narration.md`／`.m4a`**
   - 用途：有框架之後填細節，或當查閱手冊。
   - **逐區塊對齊投影片，不是主題式摘要**：投影片上有幾個區塊（每個條列點、每張公式卡、每張圖、每張卡片），講稿就有幾段對應說明，依畫面由上到下、由左到右的順序走，不跳過任何一格。每頁開頭先報這頁有幾個區塊、怎麼排列。
     - 反例：摘要有 5 點，講稿卻寫「摘要在講三件事」——區塊數對不上，使用者無法照著看。

   **兩份共通：必須報出位置，聽的人才能用手指著看**
   - 不能只說「請翻到第 4 頁」，要說**翻到第幾頁 + 看那一頁的哪一格**：「看上面那三張並排卡片的第一張」「看左邊的第二個要點」「看右上角那張公式卡」「看中間那張標了一二三四的卡片」。
   - 位置用語要跟投影片實際版面一致（左／右、上／下、第幾張卡、第幾個要點）。
   - **產生音檔（TTS）前，先確認使用者的作業系統**——TTS 工具沒有跨平台的通用解，用錯指令會直接失敗：

     | 系統 | 工具 | 說明 |
     |---|---|---|
     | **macOS** | `say -v Meijia`（台灣中文） | 系統內建、免安裝、離線。注意 `say -f` 讀 UTF-8 檔會報 `Input text is not UTF-8 encoded`（加 BOM 也無效），要把文字當**參數**傳入（例如用 Python 的 `subprocess`） |
     | **Linux** | `piper`（本地神經 TTS）或 `edge-tts` | 系統**沒有**內建堪用的中文 TTS。`espeak-ng` 雖然到處都有，但中文品質差到不適合聽完整篇。piper 需下載語音模型、可離線；edge-tts 用 pip 安裝、免金鑰但需連網 |
     | **Windows** | PowerShell 的 SAPI（`System.Speech`）或 `edge-tts` | SAPI 需要安裝中文語言包，品質普通 |
     | **跨平台首選** | `edge-tts`（pip 安裝） | 免金鑰、中文語音品質好（zh-TW-HsiaoChenNeural 等），但**文字會送到微軟的線上服務** |

     - **隱私提醒**：`edge-tts` 之類的線上服務會把講稿內容送出去。若講稿含未發表的研究內容，要先告知使用者並取得同意，或改用可離線的方案（macOS `say`、Linux `piper`）。
     - 換平台時語音名稱、參數、輸出格式都不同，不要沿用上次的指令；先確認工具是否存在（例如 `which say` / `which piper`）再產生。
   - **朗讀正規化（產生音檔前必做，講稿本身維持正確書面寫法）**：
     - **全大寫的詞會被逐字母唸出**。應該唸成一個字的改為首字大寫：`NVIDIA` → `Nvidia`、`SLERP` → `Slerp`、`NASA` → `Nasa`；本來就該逐字母唸的縮寫維持全大寫（`RMP`、`MPC`、`DMP`、`PID`、`IK`、`ABB`）。
     - **縮寫與單字連寫時，中間的字母會被吃掉**：`RMPflow` 會唸成「R-M-flow」。要加空白拆開成 `RMP flow`。
     - **希臘字母改寫成英文拼法**：α → alpha、β → beta、φ → phi、γ → gamma、σ → sigma、θ → theta、Σ → sigma、Ω → omega。
     - **孤立或成對的標點會被唸出名稱**（例如自行插入的「。」被唸成「句號」）。破折號改逗號，引號與括號移除或改逗號，行首不要留標點；最後收掉重複標點與標點前後的空白。
     - 數字寫成中文（式子二十一），避免逐位唸出。
     - 產生前把文字掃過一遍，列出所有全大寫詞、英數連寫詞、希臘字母與非常用標點，逐一確認唸法。
   - 講稿檔末附「音檔時間軸」表，方便跳到指定段落；沒有 ffmpeg 時可用字數比例估算並註明為估算值。
   - **agent 無法試聽，必須告知使用者音檔的發音品質未經確認。**

7. **存檔**
   - 產出存到該論文資料夾的 `slides/` 底下，命名格式：`<論文資料夾名>-slides.pptx`。
   - 一併存一份 `.pdf`（QA 時本來就會產生），方便快速預覽與跨機器閱讀。
   - 大型二進位檔（pptx／pdf／m4a）確認已納入 Git LFS 追蹤再 commit。

8. **收尾**
   - 向使用者說明成品與大綱的差異（若有），詢問是否需要調整。
   - 完成後建議使用者之後執行 `review` 進行完整複習。

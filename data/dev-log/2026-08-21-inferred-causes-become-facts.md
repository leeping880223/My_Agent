# 使用者沒明講的因果，agent 會自動補成「看起來合理的版本」，然後拿它當地基

- **日期**：2026-08-21
- **嘗試的方法**：使用者在對話中提到一段經歷的片段，agent 沒有追問來歷，直接把缺的部分補成一個情境上最合理的版本，寫進檔案，並拿它繼續往下推論。
- **為何失敗**：同一段經歷（在台積電的那份工作）**連錯三次，每次都是同一個機制**：

  | # | agent 寫的 | 實際 | 錯在哪 |
  |---|---|---|---|
  | 1 | 「ASML EUV 設備工程師（駐台積電）」 | **台積電的模組副工程師**，顧的機台是 ASML EUV | **雇主搞反**——供應商視角 vs 客戶端視角，對設備商職缺的價值完全不同 |
  | 2 | 「離職原因是輪班」 | 離職是**升等路徑算不過來**；不輪班是**往後的條件**，不是當初的原因 | **因果錯**——把後面提到的偏好，倒推成前面的動機 |
  | 3 | 「為了研究辭掉工作，是已付出的沉沒成本」 | 是**理性計算**：兩年內升不上去，不如去唸書，而且**唸完回去直接升等** | **性質錯**——機會成本被高估，而且漏掉「有退路」這個關鍵事實 |

  三次都是使用者主動更正才發現的。共同機制：**片段資訊 → agent 補一個合理版本 → 寫進檔案 → 當成事實往下推**。

  **危險在於它錯得很安靜。** 補出來的版本情境上都說得通，不會觸發任何檢查；而下游的推論（職涯排序、面試故事、要不要延畢）已經建立在上面了。第 2 次的錯誤直接讓篩選器設成「班別」而不是「職能」，第 3 次的錯誤支撐了一整段「所以第二階段權重要拉高」的論證——**兩段都是整段作廢重寫**。

  對照 dev-log `2026-08-14-qa-difficulty-mismatch`：那次是**題目**建立在錯的假設上；這次是**檔案**建立在錯的假設上，後果更久，因為檔案會被下一個對話讀走。

- **替代方案**：
  1. **來歷要問，不要推。** 每一段經歷的**雇主、職稱、離開的原因、當初想做什麼**——這四項是後續推論的地基，缺哪一項就問，不要補。
  2. **寫進檔案時標來源**。使用者原話 vs agent 推斷要分得出來；推斷的一律標 `⬜ 待確認`（skills.md 已在用這個做法）。
  3. **迴避型的答案要追問趨向**。「我不想做 X」不足以當條件，要問出「那你想做什麼」——**趨向型的答案才排得了序、也才寫得成面試故事**。
  4. **警訊**：當 agent 發現自己正在寫一句「因為 A，所以他 B」，而 A 不是使用者說過的話——**停下來問**。
  5. 已寫入 `skills/career/job-matching/SKILL.md` 步驟 3.3。
